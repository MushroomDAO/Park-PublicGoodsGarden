# 10. Ticket & Credential Design (门票与凭证体系)

本文档定义 Park 生态的**门票（Ticket）如何转化为可验证凭证**，以及**凭证如何门禁服务网络**。

> **Critical — 本文档的边界**
> 本文档**不是**反破解 / DRM 方案。Park 内的数字公共物品以 Apache 2.0 开源，**我们不防破解**：任何人只要有技术能力，可以直接拿走代码使用，甚至不需要支付 ¥9.9。
> 本文档要解决的问题是：**如何让未购票者无法接入 Park 的基础服务网络。**
> 这两件事完全不同，混在一起会导致大量无效投入。

---

## 🧰 0. 先划清边界：什么是免费的，什么是收费的

用「钳子与电焊」的比方来定义 Park 的经济边界：

| 层 | 比方 | 是否免费 | 说明 |
|---|---|---|---|
| **工具本体** | 钳子、电焊机 | ✅ **免费** | 源代码。Apache 2.0，可自编译、自部署、自修改、自分发。**这是真正的开源承诺。** |
| **能源** | 电力 | ❌ 收费 | 算力 / 模型推理 / API 调用。**你可以用我们的，也可以自己买别人的。** |
| **耗材** | 焊条 | ❌ 收费 | 高消耗的增量服务（复杂模型、批量任务） |
| **安装与维护** | 上门调试、保养 | ❌ 收费 | 初始化部署、技术支持、SLA。**你有技术团队可以自己搞定。** |
| **接入基础服务网络** | 电网并网 | 🎫 **门票（¥9.9）** | **本档的核心**：agent 网络接入、持续自动化更新通道、KMS/签名等基础服务 |
| **高级服务** | 工业用电套餐 | ❌ 增量付费 | 托管模型 API、GPU 额度、企业级 SLA |

**Critical — 定价的会计约束**
「一次性 ¥9.9 终身」在数学上只对**边际成本 ≈ 0** 的部分成立。
因此：**门票覆盖的是「基础服务网络的接入权」，绝不包含持续的算力消耗。**
卖电焊不包一辈子电力和焊条。任何把云端算力打包进 ¥9.9 的设计，都会在规模化后必然亏损。

### 「终身」的定义（Critical，必须在用户协议中明确）

**终身 = 持续获得该公共物品的代码版本与后续升级**，即：

- ✅ 持续的自动化更新通道（对应本文档的更新服务）
- ✅ 基础服务网络的长期接入权
- ❌ **不包含**：持续消耗的算力、模型 API 调用、第三方服务成本

参考先例：JetBrains 的 *perpetual fallback license* 把「永久」锚定在**订阅开始时的大版本**上，从而把「永久持有」与「持续迭代」分离——[JetBrains 官方 FAQ](https://sales.jetbrains.com/hc/en-gb/articles/207240845-What-is-a-perpetual-fallback-license-and-how-do-I-use-one)。

## 🔄 1. 核心结论：验证的位置必须翻转

> ### **不要试图阻止别人「使用软件」，要阻止别人「使用你的服务」。**
>
> 凡是你**能控制的资源**（网关、KMS、更新源、模型推理），就在**那个资源的入口**验票。
> 凡是你**在客户端做**的检查，都不算门禁。

这条结论推翻了一个常见的直觉（也推翻了一份早期草稿的判断）：**「每次使用都在线验证」在保护本地软件的场景下很笨，但在门禁服务网络的场景下，它是唯一正确答案。**

原因很直接：

| | 保护本地软件 | 门禁服务网络（本文档场景） |
|---|---|---|
| 攻击者在哪 | 自己的机器上，**代码归他控制** | 网络另一端，**服务器归你控制** |
| 能否被绕过 | ✅ 能，patch 掉检查即可 | ❌ **不能** |
| 验证时机 | 越频繁越烦人，且依然无效 | **越频繁越可靠，且用户无感** |
| 吊销生效 | 有离线窗口，必然滞后 | **即时** |

**一句话：他拿得走你的源代码，但拿不走你的服务器。门禁必须建在你控制的那一侧。**

## 🌐 2. 关键架构分叉：你的「agent 网络」是谁在运行？

这是决定实现方案的分水岭。**请先明确属于哪一种：**

### 情形 A · 中心化服务（你运营）

服务端 = 你运营的网关 / KMS / 更新 CDN / 模型 API。

- **门禁方式**：服务端中间件校验令牌，**每请求执行**
- **可靠性**：100%，攻击者无法触及
- **吊销**：即时生效
- **实现复杂度**：低

### 情形 B · 去中心化节点网络（社区自运行）

节点由用户/社区自己跑，节点之间互相提供服务，**没有单一入口可以拦**。

- **门禁方式**：每个节点必须**独立判断**「这个对等方有票吗」
- **可靠性**：取决于节点是否诚实执行 —— 节点可以自行放行任何人
- **吊销**：必须靠**吊销列表分发**，存在同步窗口
- **实现复杂度**：高

### 情形 C · 混合（最可能，也最推荐）

| 资源 | 归属 | 门禁方式 |
|---|---|---|
| KMS / 签名服务 | 你运营 | **情形 A** — 服务端强门禁 |
| 自动更新通道 | 你运营 | **情形 A** — 服务端强门禁 |
| 托管模型 API | 你运营 | **情形 A** — 服务端强门禁 |
| Agent P2P 网络 | 社区节点 | **情形 B** — 节点间凭证验证 |

**建议：阶段一先只做情形 A。** 情形 A 用 20% 的成本拿到 95% 的效果，因为它守住了所有真正值钱的资源。情形 B 是网络规模上来之后的事。

> **诚实提醒**：在情形 B 下，如果节点完全离线且拒绝任何同步，**技术上无法及时吊销**。这是物理约束，不是实现缺陷。详见 §5.6。

## 🎫 3. 凭证模型：三层

因为**本地软件不需要保护**，凭证体系的目标从「防复制」变成了「**限制席位 + 门禁服务**」。

```
Ticket（¥9.9 门票，1 份）
  │  = 服务网络的接入权，记录在 Park 身份/账本系统
  │
  ├─ Seat #1 ── Device A（硬件密钥对，不可导出）
  ├─ Seat #2 ── Device B
  ├─ Seat #3 ── （空）
  └─ Seat #4 ── （空）        seats_total 恒为 4
        │
        └─ Session Token（短时效，DPoP 绑定到该设备公钥）
              = 每次调用服务时出示的东西
```

| 层 | 名称 | 回答的问题 | 时效 | 存放位置 |
|---|---|---|---|---|
| L1 | **Ticket** | 这个人买了门票吗？ | 终身 | Park 身份系统 / 链上 |
| L2 | **Seat** | 这台硬件被允许接入吗？ | 随 Ticket 存续 | 服务端登记 + 本地硬件密钥 |
| L3 | **Session Token** | 这一次调用合法吗？ | 5~15 分钟 | 内存 |

### 为什么还需要硬件绑定？

**不是为了防复制软件，而是为了防「账号共享」。**

一张 ¥9.9 的门票，如果只是一个账号密码，它可以被无限多人共用 —— 一个人买票，全公司乃至全网都觉得「反正能登上去」。**4 个席位 + 硬件绑定**把这件事变成可管理、可撤销、有摩擦的。

| 目的 | 手段 |
|---|---|
| 防账号在天南地北被 100 人同时用 | **席位上限 + 硬件密钥绑定** |
| 防凭证文件被拷走直接用 | **硬件内不可导出的私钥**（复制出去没有对应私钥，密码学上无效） |
| 防令牌被中间人截获重放 | **DPoP 发送方约束令牌**（RFC 9449） |

**Critical — 不要用机器指纹，要用硬件密钥。**
机器指纹（MAC、主板序列号、磁盘 ID）可伪造、可虚拟化、可被 hook 绕过，属于**混淆式绑定**；TPM 2.0 / Apple Secure Enclave / Android Keystore 的**不可导出私钥**才是**密码学绑定**。已有的商业 SDK 中，Keygen 的 license file 本质是「license key + 机器指纹」派生的 AES 密钥解密，**强度低于硬件密钥方案**，若要采用需自行替换绑定层。

### 不需要的东西（明确排除）

| 方案 | 为什么不用 |
|---|---|
| 零知识证明 / Semaphore | 匿名与硬件绑定在今日可部署技术下**本质互斥**（attestation 天生可链接）；本场景不需要匿名，只需门禁 |
| 区块链 / 智能合约 | 每请求上链成本与延迟不可接受；中心化门禁已经 100% 可靠。链只在**席位登记需要公开可审计**时才有价值 |
| 匿名凭证（Privacy Pass / PAT） | 解决的是「匿名地通过速率限制」，与「限制到 4 台设备」目标相反 |
| 重型 DRM / 代码混淆 | 源代码公开，混淆无意义（见 §7） |

## 🔐 4. 验证逻辑（核心）

### 4.1 购票与开通

```
用户支付 ¥9.9
   → 创建 Ticket { ticket_id, owner, seats_total: 4, seats_used: 0, status: active }
   → 发放 Park ID（对应既有 MySBT，见 §8）
```

自助获取，无人工介入。既有的 **Paymaster / Box Office** 负责法币与稳定币的收款与兑换。

### 4.2 设备注册（占用一个席位）

这是**唯一的离线可完成部分**，但注册动作本身需要一次在线交互：

```
1. 设备本地生成密钥对
     私钥 → 写入 Secure Enclave / TPM 2.0 / Android Keystore（不可导出）
     公钥 → device_pubkey

2. 设备向服务端请求 challenge（随机数，一次性、短时效）

3. 设备用私钥签名 challenge，连同 device_pubkey 上报

4. 服务端校验：
     a. 签名有效 ← 证明它真的持有该私钥（而非仅仅报了一个公钥）
     b. seats_used < seats_total
     c. 重绑冷却期已过（见 §4.5）
     d. 【可选加分】Attestation 校验（App Attest / Play Integrity）

5. 通过 → 登记 Seat { seat_id, ticket_id, device_pubkey, status: active }
        seats_used += 1
```

**Critical — 不要用「服务端生成凭证字符串发给客户端」的方式。**
凭证必须以**命名了某设备公钥的签名声明**形式存在。这样即使凭证文件被完整拷贝到另一台机器，对方也**无法出示对应私钥的签名**，凭证在那里就是废纸。

> **Attestation 是加分项，不是硬门槛。**
> 固件 TPM（Intel PTT / AMD fTPM）**可能没有 EK 证书**，硬性要求会导致一批真实付费用户被误杀。建议策略：能 attest 则提升信任等级，不能则降级放行。

### 4.3 换取会话令牌（DPoP）

采用 **OAuth 2.0 DPoP（RFC 9449）** 的发送方约束令牌模型：

```
设备 → 服务端：POST /token
   携带 DPoP proof（用设备私钥签名的 JWT，含 htm / htu / iat / jti / jwk）

服务端签发 access token，并在其中写入：
   cnf.jkt = SHA-256 thumbprint(device_pubkey)
```

**效果**：令牌被截获也没用 —— 攻击者没有设备私钥，签不出合法的 proof。

### 4.4 每次调用：服务端门禁（This is the gate）

**这是整个方案的核心。** 所有受保护服务的前置中间件：

```
请求 → 网关
  ├─ 1. 校验 access token 签名与有效期
  ├─ 2. 重算 DPoP proof 中公钥的 thumbprint，要求 == token 的 cnf.jkt
  ├─ 3. 校验 proof 的 htm / htu / iat / jti（防重放）
  ├─ 4. 查 Ticket 与 Seat 状态（active / revoked / suspended）
  ├─ 5. 配额与速率限制（按 Ticket 等级）
  ├─ 6. 计费（若为增量付费服务）
  └─ 7. 放行 → 记录用量
```

**关键性质：以上每一步都在你的服务器上执行。** 攻击者能改的只有客户端，改不了这里。

> 对照既有文档：这与 `05_Mechanism_Design.md` 中「防搭便车」一节完全一致 —— 「门票不是为了收费，而是为了筛选。只有支付了押金/年费的用户才能调用 API」。**本文档是该原则的凭证层落地。**

### 4.5 撤销与重绑

服务端两种语义，**必须区分**（参考 Cryptlex 的既有实践）：

| 动作 | 语义 | 适用场景 | 效果 |
|---|---|---|---|
| **Suspend** | 暂停该席位 | 用户换设备、临时异常 | 该设备无法续令牌，**记录保留，可恢复** |
| **Revoke** | 永久废除此席位 | 退款、违规、滥用 | 席位作废，`seats_used -= 1`，用户可重新绑定新硬件 |

**重绑**：撤销后释放的席位可以绑定新硬件，**总数恒为 4**。
（注意：是「当前有效席位数 ≤ 4」，不是「累计只能绑 4 次」—— 这一点必须在产品文案中说清楚，否则会引发客诉。）

**Critical — 必须加重绑节流。**
否则 4 个席位的冷却期约等于 0 时，一票可以喂饱无限多人（轮流占用）。建议：

- 席位重绑冷却：**30 天 / 次**
- 或设置终身重绑次数预算

**在线场景下的最大优势**：因为每次调用都过网关、令牌又是短时效，**吊销是即时生效的**，不存在离线方案里那个「撤销窗口」。这是选择情形 A 的核心理由之一。

### 4.6 去中心化节点（情形 B）的降级方案

当节点由社区自运行时，节点需要**独立**判断对等方是否有票：

```
Issuer（你）签发 → Signed Entitlement（含 device_pubkey / seat_id / not_after）
                         ↓ 分发
节点内置 Issuer 公钥，离线验签 → 放行
```

**吊销的代价（必须诚实接受）：**

> **吊销延迟下界 = 离线凭证的有效期。**
> 要让吊销在 N 天内生效，离线凭证最长只能活 N 天，于是节点每 N 天必须联网同步一次。

落地方案：短时效 Lease（建议 7~30 天）+ 周期性拉取吊销列表。

⚠️ **注意**：W3C Bitstring Status List 虽然已成 Recommendation，但它的 Validate 算法**第一步就是 dereference `statusListCredential` URL** —— 它是**保护隐私的在线吊销机制，不是离线方案**，节点必须定期联网拉取。

**结论**：情形 B 的吊销能力**结构性地弱于**情形 A。若社区节点长期离线，只能退化为「事后追责」。

## ⚙️ 5. 参数建议

| 参数 | 建议值 | 依据 |
|---|---|---|
| Ticket 时效 | **终身**（= 代码版本 + 后续升级） | 见 §0 |
| 席位上限 | **4** | 产品定义 |
| 席位重绑冷却 | **30 天 / 次** | 防账号共享轮换 |
| Session Token TTL | **5~15 分钟** | 在线场景，越短越安全，刷新无感 |
| 设备绑定原语 | Secure Enclave / TPM 2.0 / Android Keystore **原生密钥** | 不可导出私钥是唯一真绑定 |
| ❌ 不要用 | Passkey（BE 位无法强制为 0，会随 iCloud/Google 同步）、机器指纹 | 会导致 4 台上限形同虚设 |
| 令牌绑定 | **DPoP（RFC 9449）** `cnf.jkt` | 截获即失效 |
| Attestation | **加分项，非硬门槛** | 固件 TPM 可能无 EK 证书 |
| 离线节点 Lease（情形 B） | **7~30 天** | 吊销窗口 = Lease 时长 |
| 限流 | 按 Ticket 等级分级 | 对应 `park.json` 的 `free_tier` / `premium_tier` |

## 🚫 6. 反模式

1. **在客户端做门禁** —— 源代码公开，改一行就绕过。客户端只能做「体验优化」，不能做「准入判定」。
2. **把凭证做成可复制的 bearer 字符串** —— 复制即盗用，且无法离线判定。必须绑定设备公钥。
3. **用机器指纹代替硬件密钥** —— 可伪造、可虚拟化。
4. **试图防破解** —— 与 Apache 2.0 承诺自相矛盾，且投入产出比极低（见 §7）。
5. **席位无重绑节流** —— 4 台设备 = 4 个人轮流共用。
6. **把云端算力打包进 ¥9.9** —— 会计上必亏。
7. **用 Passkey 做设备绑定** —— BE（Backup Eligibility）位无法可靠强制为 0，凭据会跟随 iCloud/Google 同步到其它设备。
8. **忽略令牌重放** —— 必须校验 DPoP proof 的 `jti` / `iat`，并支持服务端 nonce。
9. **忘了时钟问题** —— 短时效令牌依赖可信时间，需单调时钟 + 服务端时间锚。

## 💰 7. 破解经济学：为什么我们不做 DRM

**「你有源代码，什么都能干，甚至可以复制我们整个体系。」—— 这是对的，而且我们接受。**

因为复制的**成本结构**决定了它不可规模化：

| 复制者需要自建 | 成本 |
|---|---|
| KMS / 密钥管理 | 工程 + 运维 + 安全审计 |
| 自动更新管道与签名分发 | 持续基础设施投入 |
| 模型托管与推理算力 | **真金白银的边际成本** |
| 节点网络与网络效应 | **无法复制，只能长出来** |
| 身份、信誉、争议仲裁 | 生态长期积累 |

**因此 Park 的护城河是「网络效应 + 更新管道 + 托管服务 + 信任」，不是代码。**

这与既有的开源商业先例一致：Red Hat 的代码自由，订阅买的是认证构建、更新与支持；GitLab / Sentry 等 open core 模式同理。

> **战略结论：不要在 DRM 上花一分钱，要把钱花在让网络本身更有价值上。**
> 破解者能拿走的是工具，拿不走的是电网。

## 🔗 8. 与既有 Park 机制的咬合

| 既有组件 | 本文档中的角色 |
|---|---|
| **GT / MySBT**（`05_Mechanism_Design.md` §1） | 即 **L1 Ticket**。GT 定义为「协议认可和加入的凭证…可以理解为门票、VIP Card」，且不可转让 —— 与本文档的席位制天然一致 |
| **Paymaster / Box Office**（`06` §2） | 购票入口，法币/稳定币收款，触发 Ticket 创建 |
| **Validator Network**（`06` §4） | 情形 B 的节点；也承载 §4.6 的吊销列表分发 |
| **`park.json`**（`05` §3） | `free_tier` / `premium_tier` 直接映射为本文档 §4.4 步骤 5 的配额与计费策略 |
| **Vault**（`05` §2） | 门票收入的调节枢纽，与本文档无关但共享同一账本 |
