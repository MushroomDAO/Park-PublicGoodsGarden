# 10. Ticket & Credential Design (门票与凭证体系)

本文档定义 Park 生态的**门票（Ticket）如何转化为可验证凭证**，以及**凭证如何在去中心化节点网络中门禁服务访问**。

> **Critical — 本文档的边界**
> 本文档**不是**反破解 / DRM 方案。Park 内的数字公共物品以 Apache 2.0 开源，**我们不防破解**：任何人只要有技术能力，可以直接拿走代码使用，甚至不需要支付 ¥9.9。
> 本文档要解决的问题是：**如何让未购票者无法接入 Park 的基础服务网络。**
> 这两件事完全不同，混在一起会导致大量无效投入。

> **文档状态**：Draft v3 · 架构已定为**情形 B（去中心化节点网络）**；计费原则**按量优先**；节点按用户支付分成；Issuer 为多签（建议 FROST 门限签名）

---

## 🧰 0. 先划清边界：什么是免费的，什么是收费的

用「钳子与电焊」的比方来定义 Park 的经济边界：

| 层 | 比方 | 是否免费 | 说明 |
|---|---|---|---|
| **工具本体** | 钳子、电焊机 | ✅ **免费** | 源代码。Apache 2.0，可自编译、自部署、自修改、自分发。**这是真正的开源承诺。** |
| **能源** | 电力 | ❌ 收费（**按量**） | 算力 / 模型推理 / API 调用。可以用我们的，也可以自己买别人的。 |
| **耗材** | 焊条 | ❌ 收费（**按量**） | 高消耗的增量服务（复杂模型、批量任务） |
| **安装与维护** | 上门调试、保养 | ❌ 收费 | 初始化部署、技术支持、SLA。有技术团队可以自己搞定。 |
| **接入基础服务网络** | 电网并网 | 🎫 **门票（¥9.9）** | agent 网络接入、持续自动化更新通道、KMS/签名等基础服务 |
| **高级服务** | 工业用电套餐 | ❌ 增量付费 | 托管模型 API、GPU 额度、企业级 SLA |

**Critical — 定价的会计约束**
「一次性 ¥9.9 终身」在数学上只对**边际成本 ≈ 0** 的部分成立。
**门票覆盖的是「基础服务网络的接入权」，绝不包含持续的算力消耗。**
卖电焊不包一辈子电力和焊条。任何把云端算力打包进 ¥9.9 的设计，都会在规模化后必然亏损。

### 「终身」的定义（Critical，必须在用户协议中明确）

**终身 = 持续获得该公共物品的代码版本与后续升级**：

- ✅ 持续的自动化更新通道
- ✅ 基础服务网络的长期接入权
- ❌ **不包含**：持续消耗的算力、模型 API 调用、第三方服务成本

参考先例：JetBrains 的 *perpetual fallback license* 把「永久」锚定在**订阅开始时的大版本**上，从而把「永久持有」与「持续迭代」分离 —— [JetBrains 官方 FAQ](https://sales.jetbrains.com/hc/en-gb/articles/207240845-What-is-a-perpetual-fallback-license-and-how-do-I-use-one)。

## 🔄 1. 两条核心原则

### 原则一：验证必须发生在资源入口

> **不要试图阻止别人「使用软件」，要阻止别人「使用你的服务」。**
> 凡是你**能控制的资源**（网关、KMS、更新源、模型推理），就在**那个资源的入口**验票。
> 凡是你**在客户端做**的检查，都不算门禁。

这推翻了一个常见直觉：**「每次使用都在线验证」在保护本地软件的场景下很笨，但在门禁服务网络的场景下，它是唯一正确答案。**

| | 保护本地软件 | 门禁服务网络（本文档场景） |
|---|---|---|
| 攻击者在哪 | 自己的机器，**代码归他控制** | 网络另一端，**资源归服务方控制** |
| 能否被绕过 | ✅ 能，patch 掉检查即可 | ❌ **不能** |
| 验证时机 | 越频繁越烦人，且依然无效 | **越频繁越可靠，且用户无感** |

**一句话：他拿得走你的源代码，但拿不走你的服务。门禁必须建在提供服务的那一侧。**

### 原则二：按量计费本身就是最强的门禁

> **如果每一次使用都在计费，那么「多一个人用」不构成损失，而是多一份收入。**
> 复制凭证、多人共用、甚至转卖账号，在按量模型下都只是**更多消费**。

**因此门禁的真正对象不是「使用行为」，而是「不计量 / 包干 / 边际成本非零的额度」。**

| 资源类型 | 需要席位门禁吗 | 理由 |
|---|---|---|
| 按量计费的算力 / API | ❌ **不需要** | 谁用谁付费，复制无害 |
| 门票自带的**免费额度** | ✅ 需要 | 不计量，可被无限白嫖 |
| 不计量的基础服务（更新通道、KMS 签名） | ⚠️ 轻度需要 | 边际成本低但非零，主要用于反滥用 |
| 身份 / 信誉 / 治理权 | ✅ 需要 | 防 Sybil、防刷号、防刷免费额度 |

> **这就是为什么「4 台设备」的定位是「反滥用机制」而不是「收费闸门」。**
> 同一个席位被 4 个人用，在按量计费下不造成收入损失 —— 它只让那 4 个人消耗得更快、付得更多。

## 🌐 2. 架构决策：情形 B（去中心化节点网络）

> **决策已确认：Park 的 agent 网络属于情形 B —— 节点由社区/用户自运行。**

节点之间互相提供算力 / 存储 / 签名服务，**没有单一入口可以拦截**。这带来以下结构性后果：

| 维度 | 情形 A（中心化） | **情形 B（已选定）** |
|---|---|---|
| 谁来验票 | 你运营的网关 | **每一个节点各自验** |
| 凭证形式 | 每次请求在线校验 | **必须能离线验签**（节点内置 Issuer 公钥） |
| 吊销延迟 | 即时 | **有窗口** = 离线凭证的 Lease 有效期 |
| 计量位置 | 你的服务器 | **在节点本地** |
| 实现复杂度 | 低 | **高** |

### 2.1 混合中的例外：这些资源仍建议走情形 A

即使网络是去中心化的，以下资源仍由 Park 侧运营，建议保留中心化强门禁：

- **自动更新通道**（分发的是你签名的构建产物）
- **KMS / 签名服务**
- **托管模型 API**

> 建议：**值钱的、你运营的资源走 A；P2P 网络本身走 B。**

### 2.2 节点激励：已定方案与残余风险

> **✅ 决策已定：节点收入 = 按用户支付分成（不是协议挖矿奖励）。**

这个选择直接决定了节点是否愿意认真验票：

| 节点的收入来源 | 它的行为倾向 |
|---|---|
| **按用户支付分成**（✅ **已选定**） | ✅ **主动严格验票** —— 放白嫖进来等于白烧自己的算力 |
| 靠协议 Infra Mining / Proof of Service 挖矿奖励 | ⚠️ 有动机与假用户串通刷量（伪造服务记录即可套奖励） |

**「按用户支付分成」消除了刷量动机**，原因是结构性的：伪造用量不产生收入，只产生成本——除非协议额外补贴，而本方案没有。

> **因此本文档 v2 中「§2.2 节点串通刷量」的风险等级由「高」降为「低」。**
> 既有 `06_Technical_Architecture.md` §4 的 `Proof of Service heartbeat` 与 `Slashing` 应重新定位为**服务可用性保障**（防宕机、防双重签名），而**不是**防刷量的主要手段。

**⚠️ 但「按用户支付分成」引入了一个新的、必须正面处理的风险：去中介化（Disintermediation）。**

| 攻击方式 | 描述 | 后果 |
|---|---|---|
| **私下交易** | 用户与节点绕过 Park 直接结算，不经过计量与分成 | Park 失去分成收入，且**用量不可见** |
| **节点自建闭环** | 节点把 Park 的凭证体系复制一份，自成小生态 | 网络效应被切分 |

**缓解方向：**

1. **让 Park 提供节点无法自建的东西** —— 统一身份/信誉、跨节点发现与路由、争议仲裁、更新管道
2. **让「在网内交易」比「私下交易」更划算** —— 分成比例、信誉加成、纠纷保护
3. **技术层面弱化强制、强化激励** —— 强制不可行（节点可改代码），但用户选择留在网内的理由是**其他节点也在网内**

> **Critical**：去中介化是**经济问题，不是密码学问题**。
> 靠凭证体系无法阻止用户和节点私下成交；只能靠"留在网内更有价值"来降低它的发生率。

## 🎫 3. 凭证模型：三层

```
Ticket（¥9.9 门票，1 份）
  │  = 服务网络的接入权，记录在 Park 身份/账本系统
  │
  ├─ Seat #1 ── Device A（硬件密钥对，不可导出）
  ├─ Seat #2 ── Device B
  ├─ Seat #3 ── （空）
  └─ Seat #4 ── （空）        seats_total 恒为 4
        │
        └─ Entitlement / Session（短时效，绑定设备公钥）
              = 节点每次服务时验证的东西
```

| 层 | 名称 | 回答的问题 | 时效 | 存放位置 |
|---|---|---|---|---|
| L1 | **Ticket** | 这个人买了门票吗？ | 终身 | Park 身份系统 |
| L2 | **Seat** | 这台硬件被允许接入吗？ | 随 Ticket 存续 | 服务端登记 + 本地硬件密钥 |
| L3 | **Entitlement / Session** | 这一次服务合法吗？ | 5~15 分钟（A）/ 7~30 天（B） | 内存或本地 |

### 为什么还需要硬件绑定？

**不是为了防复制软件（软件已开源），而是为了反滥用：**

| 目的 | 手段 |
|---|---|
| 防免费额度被无限白嫖 | **席位上限 + 硬件密钥绑定** |
| 防凭证文件被拷走直接用 | **硬件内不可导出的私钥**（复制出去没有对应私钥，密码学上无效） |
| 防令牌被截获重放 | **DPoP 发送方约束令牌**（RFC 9449） |
| 让行为可归因，支撑信誉与仲裁 | **设备级身份** |

**Critical — 不要用机器指纹，要用硬件密钥。**
机器指纹（MAC、主板序列号、磁盘 ID）可伪造、可虚拟化、可被 hook 绕过，属于**混淆式绑定**；TPM 2.0 / Apple Secure Enclave / Android Keystore 的**不可导出私钥**才是**密码学绑定**。

### 不需要的东西（明确排除）

| 方案 | 为什么不用 |
|---|---|
| 零知识证明 / Semaphore / 匿名凭证 | 匿名与硬件绑定在今日可部署技术下**本质互斥**（attestation 天生可链接）；本场景需要的是可归因，不是匿名 |
| 逐笔上链 | 每请求上链成本与延迟不可接受；链只在**席位登记需要公开可审计**时有价值 |
| 重型 DRM / 代码混淆 | 源代码公开，混淆无意义（见 §7） |

## 🔐 4. 验证逻辑

### 4.1 购票与开通

```
用户支付 ¥9.9
   → 创建 Ticket { ticket_id, owner, seats_total: 4, seats_used: 0, status: active }
   → 发放 Park ID（对应既有 MySBT）
```

自助获取，无人工介入。既有 **Paymaster / Box Office** 负责法币与稳定币收款。

### 4.2 设备注册（占用一个席位）

```
1. 设备本地生成密钥对
     私钥 → 写入 Secure Enclave / TPM 2.0 / Android Keystore（不可导出）
     公钥 → device_pubkey

2. 设备向 Issuer 请求 challenge（随机数，一次性、短时效）

3. 设备用私钥签名 challenge，连同 device_pubkey 上报

4. Issuer 校验：
     a. 签名有效 ← 证明它真的持有该私钥（而非仅仅报了一个公钥）
     b. seats_used < seats_total
     c. 【可选加分】Attestation 校验（App Attest / Play Integrity）

5. 通过 → 登记 Seat { seat_id, ticket_id, device_pubkey, status: active }
        seats_used += 1
```

**Critical — 不要用「服务端生成凭证字符串发给客户端」的方式。**
凭证必须以**命名了某设备公钥的签名声明**形式存在。这样即使被完整拷贝到另一台机器，对方也**无法出示对应私钥的签名**。

> **Attestation 是加分项，不是硬门槛。**
> 固件 TPM（Intel PTT / AMD fTPM）**可能没有 EK 证书**，硬性要求会误杀真实付费用户。

### 4.3 签发可离线验证的授权凭证

因为**节点必须能独立验证**（情形 B），凭证形态为：

```
SignedEntitlement {
    seat_id,
    device_pubkey,
    ticket_id,
    tier,              // 服务等级 / 免费额度
    not_before,
    not_after,         // ← 吊销窗口由这个字段决定
    issuer_sig         // Issuer 私钥签名
}
```

节点内置 **Issuer 公钥**，离线验签即可放行，无需回连中心。

#### Issuer 采用门限签名（已定：多签）

> **✅ 决策已定：Issuer = 多签集合。**

但**不要把「多签列表」直接暴露给节点**——那会迫使每个节点实现 N 个公钥的验证、门限判断、以及签名者集合变更后的元数据同步，节点端复杂度陡增，而这正是去中心化网络最容易出错的地方。

**推荐实现：门限签名（Threshold Signature）。**

使用 [RFC 9591 FROST](https://www.rfc-editor.org/rfc/rfc9591.html)（Flexible Round-Optimized Schnorr Threshold Signatures），把 N 个签名方的密钥份额合成**一把公钥**：

| | 多签列表（Multisig） | **门限签名（FROST，推荐）** |
|---|---|---|
| 签名产物 | N 个独立签名的集合 | **单个签名** |
| 节点需要内置 | N 个公钥 + 门限逻辑 | **1 个公钥** |
| 签名方集合变更 | 节点必须同步新列表 | 公钥不变，**节点无感** |
| 节点端复杂度 | 高 | **与单签一致** |

**效果**：签名权分散在 M-of-N 个持有者（例如 3-of-5）之间，任何单点被攻破都无法伪造凭证；而**节点端只需要验一个公钥，零额外复杂度**。

### 4.4 节点侧的门禁（情形 B 的核心）

```
请求到达节点
  ├─ 1. 验证 SignedEntitlement 的 Issuer 签名
  ├─ 2. 校验 not_before / not_after（凭证是否在有效期）
  ├─ 3. 校验持有者证明（PoP）：用 device_pubkey 验证请求方对 challenge 的签名
  │        ← 这一步使「复制凭证」无效
  ├─ 4. 校验凭证未被吊销（对比近期同步的吊销列表）
  ├─ 5. 计量与配额（核心！按量计费在此执行）
  ├─ 6. 提供服务 → 记录用量 → 结算
  └─ 7. 放行
```

**第 5 步是情形 B 真正的门禁**：即使有人绕过了前四步，他产生的消费依然要被计量和结算。

### 4.5 席位与重绑：反滥用机制，不是收费闸门

**Critical — 这一节的定位已修正（v1 曾表述为「必须加重绑节流」）。**

在**按量计费**模型下，多人共用席位**不造成收入损失**（用得多就付得多），因此：

| 场景 | 是否需要重绑冷却 |
|---|---|
| 纯按量计费的服务 | ❌ **不需要** —— 共用 = 多消费 = 多付费 |
| 门票自带的**不计量免费额度** | ✅ **需要** —— 否则可轮换刷额度 |
| 不计量的基础服务（KMS 签名、更新带宽） | ⚠️ 建议加（如 30 天/次），防止成本被无限分摊 |

**重绑的语义**（参考 Cryptlex 的既有实践）：

| 动作 | 语义 | 适用场景 |
|---|---|---|
| **Suspend** | 暂停席位，记录保留可恢复 | 换设备、临时异常 |
| **Revoke** | 永久废除此席位，`seats_used -= 1` | 退款、违规、滥用 |

**注意**：是「当前有效席位数 ≤ 4」，不是「累计只能绑 4 次」—— 必须在产品文案中写清楚。

### 4.6 吊销：情形 B 的诚实限制

> **吊销延迟下界 = 离线凭证的有效期。**
> 要让吊销在 N 天内生效，凭证最长只能活 N 天，于是节点每 N 天必须联网同步一次。

**这是结构性的，无法通过技术消除。** 落地方案：

- 短时效 Lease（建议 7~30 天）+ 周期性拉取吊销列表
- ⚠️ **W3C Bitstring Status List 虽然已成 Recommendation，但它的 Validate 算法第一步就是 dereference `statusListCredential` URL** —— 它是**保护隐私的在线吊销机制，不是离线方案**，节点必须定期联网拉取

**残余风险**：若节点长期离线，凭证可在吊销后继续使用至 Lease 过期。
**缓解手段只有一条——依赖计量**：即使被滥用，消费依然被记录和计费，损失被限制在一个 Lease 周期内的用量，而非无限期。

#### Lease 续期 ≠ 重新登录（常见误解）

> **续期是后台静默的机器动作，用户完全无感。不是「每 30 天让你重新登录一次」。**

| | 重新登录 | **Lease 续期** |
|---|---|---|
| 谁发起 | 用户手动输入账号密码 | **客户端后台自动** |
| 用户感知 | 明确的中断 | **无感，不可见** |
| 触发条件 | 会话失效、换设备 | 定时器到期 + 网络可达 |
| 失败表现 | 弹登录框 | **宽限降级**（见下） |

**设计目标：用户永远不该意识到 Lease 的存在。**

设备联网时，客户端在到期前静默续上一张新 Lease。只有**设备长期离线**导致 Lease 过期时，才进入宽限降级——参考 Adobe 的三段式（静默 → 可关闭提示 → 每日提示 → 最后一次使用），**而不是弹登录框**。等设备恢复联网，自动续上即可。

### 4.7 「不计量免费额度」清单（待逐项定义）

> **背景**：§1 原则二指出，席位门禁只对**不计量**的资源有意义。因此必须先把「哪些是不计量免费额度」列清楚，否则无法判断要不要启用重绑冷却。

**判据三问：**

1. 该服务的**边际成本 > 0** 吗？
2. 能否**准确计量**单次消耗？
3. 成本由**谁承担**（Park / 节点 / 用户）？

**分类矩阵：**

| 边际成本 | 可计量 | 处置 | 需要席位 / 冷却吗 |
|---|---|---|---|
| ≈ 0 | — | 免费开放（仍可要求持票） | ❌ 不需要 |
| > 0 | ✅ 可计量 | **按量计费** | ❌ 不需要 —— **计量本身就是门禁** |
| > 0 | ❌ 难计量 | **必须设硬额度** | ✅ **需要** ← **唯一真正需要冷却的象限** |

**候选清单（需团队逐项确认并补齐）：**

| 服务 | 边际成本 | 可计量 | 成本归属 | 建议处置 |
|---|---|---|---|---|
| 代码 / 构建产物下载 | ≈0 | — | Park | 免费，凭票 |
| 自动更新通道 | 低（带宽） | ✅ 按 GB | Park | 免费额度（如 5 GB/月）+ 超额按量 |
| KMS / 签名服务 | ≈0 | ✅ 按次 | Park | 免费额度（如 N 次/日）+ 超额按量 |
| Park ID / 信誉 / 治理参与 | ≈0 | — | Park | 免费，**持票即得**（这就是门票本身） |
| Agent 网络寻址 / 发现 | 低 | ✅ 按查询 | 节点 | 免费额度 + 超额按量 |
| 托管模型推理 | **高** | ✅ 按 token | Park | **按量计费** |
| 社区节点算力 | **高** | ✅ 按 token / 秒 | 节点 | **按量计费 + 按用户支付分成** |
| 存储 | 高（持续） | ✅ 按 GB·天 | 节点 | 按量计费 |
| **免费试用额度** | **高** | ❌ 难（用户可不计量地占用） | Park | ⚠️ **必须严格席位 + 重绑冷却** |

> **结论**：真正需要「席位上限 + 重绑冷却」的，当前**只有「免费试用额度」这一类**。
> 其余要么边际成本 ≈ 0（免费开放即可），要么可计量（按量计费，计量即门禁）。

## ⚙️ 5. 参数建议

| 参数 | 建议值 | 依据 |
|---|---|---|
| Ticket 时效 | **终身**（= 代码版本 + 后续升级） | 见 §0 |
| 席位上限 | **4** | 产品定义 |
| 席位重绑冷却 | **仅对不计量额度启用**（如 30 天/次）；纯按量服务可省略 | 见 §4.5 |
| Entitlement Lease 时长 | **7~30 天** | 吊销窗口 = Lease 时长 |
| Session Token TTL | **5~15 分钟** | 若节点本地签发 |
| 设备绑定原语 | Secure Enclave / TPM 2.0 / Android Keystore **原生密钥** | 唯一真绑定 |
| ❌ 不要用 | Passkey（BE 位无法强制为 0，会随 iCloud/Google 同步）、机器指纹 | 会让 4 台上限形同虚设 |
| 持有者证明 | **DPoP（RFC 9449）** `cnf.jkt` | 使复制的凭证无效 |
| Attestation | **加分项，非硬门槛** | 固件 TPM 可能无 EK 证书 |
| 计量粒度 | 按请求 / 按 token / 按秒 | 决定收费模型，**是真正的门禁** |
| Issuer 签名方案 | **门限签名 FROST（RFC 9591）**，建议 3-of-5 | 节点端只需内置 1 个公钥，签名方变更时节点无感 |
| 节点收入模型 | **按用户支付分成** | 消除刷量动机（§2.2） |
| Lease 续期方式 | **后台静默自动**，不进登录流程 | 用户不可感知（§4.6） |

## 🚫 6. 反模式

1. **在客户端做门禁** —— 源代码公开，改一行就绕过。客户端只能做体验优化，不能做准入判定。
2. **把凭证做成可复制的 bearer 字符串而不绑定公钥** —— 复制即盗用。必须加持有者证明（PoP）。
3. **用机器指纹代替硬件密钥** —— 可伪造、可虚拟化。
4. **试图防破解** —— 与 Apache 2.0 承诺自相矛盾，且投入产出比极低（见 §7）。
5. **对所有资源都套用席位限制** —— 按量计费的资源不需要席位门禁，只会增加无谓摩擦。
6. **把云端算力打包进 ¥9.9** —— 会计上必亏。
7. **用 Passkey 做设备绑定** —— BE 位无法可靠强制为 0。
8. **忽略令牌重放** —— 必须校验 PoP 证明的 `jti` / `iat`，并支持服务端 nonce。
9. **忘记时钟问题** —— 短时效凭证依赖可信时间，需单调时钟 + 服务端时间锚。
10. **在情形 B 中只设计密码学、不设计激励** —— 见 §2.2，节点串通刷量是经济攻击，密码学挡不住。

## 💰 7. 破解经济学：为什么我们不做 DRM

**「你有源代码，什么都能干，甚至可以复制我们整个体系。」—— 这是对的，而且我们接受。**

因为复制的**成本结构**决定了它不可规模化：

| 复制者需要自建 | 成本 |
|---|---|
| KMS / 密钥管理 | 工程 + 运维 + 安全审计 |
| 自动更新管道与签名分发 | 持续基础设施投入 |
| 算力与推理 | **真金白银的边际成本** |
| 节点网络与网络效应 | **无法复制，只能长出来** |
| 身份、信誉、争议仲裁 | 生态长期积累 |

**因此 Park 的护城河是「网络效应 + 更新管道 + 托管服务 + 信任」，不是代码。**

> **战略结论：不要在 DRM 上花一分钱，要把钱花在让网络本身更有价值上。**
> 破解者能拿走的是工具，拿不走的是电网。

## ❓ 9. 待决与未核实

**已决策：**

1. ✅ agent 网络 = **情形 B**（去中心化节点网络）
2. ✅ 计费原则 = **按量优先**；席位定位为**反滥用**，不是收费闸门
3. ✅ 节点奖励 = **按用户支付分成**（非 Proof of Service 挖矿）→ §2.2 刷量风险降为低
4. ✅ Issuer = **多签集合** → 建议实现为**门限签名（FROST / RFC 9591）**，节点端零额外复杂度
5. ✅ Lease 续期为**后台静默**，**不要求用户重新登录**（§4.6）

**待决策：**

6. **「不计量免费额度」清单** —— 见 §4.7，需团队逐项确认（**当前无法一次性回答，属正常**）
7. Entitlement Lease 时长取值（建议 7~30 天 = 吊销窗口）
8. 门限签名的门限值 N-of-M（建议 3-of-5）
9. **去中介化的缓解策略**（§2.2）—— 分成比例、信誉加成、纠纷保护如何设计

**未核实（引用前请复核）：**
