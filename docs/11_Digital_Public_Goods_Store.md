# 11. Digital Public Goods Store (数字公共物品商店)

> **一句话定义**
> 一个**会员制**的数字公共物品商店：支付 **¥9.9** 铸造一枚 SBT 会员凭证，即可**无限免费下载**店内任何数字公共物品；**API 与算力服务由社区节点提供**，按量计费，或使用 **BYOK**（自带密钥）完全免费。

> **文档状态**：Concept v1 · 配套可点击原型：`prototype/digital-public-goods-store.html`

---

## 💡 0. 核心洞察：商店的两半，两种经济学

这是整个产品能否成立的**唯一关键判断**：

| 商店的两半 | 交付物 | 边际成本 | 定价策略 |
|---|---|---|---|
| **下载** | 代码、模型权重、构建产物 | **≈ 0** | 会员**无限免费** ✅ |
| **API / 算力** | 推理、托管服务 | **> 0** | **按量计费** 或 **BYOK** |

**因此「¥9.9 无限下载」在经济学上是安全的**——因为多一个人下载，你多花的钱是零。

而 **BYOK 不是附加功能，它是让「终身免费」成立的支点**：

```
Park 提供算力   → 边际成本 > 0 → 必须计量 → 不可能"终身免费"
用户自带密钥     → 边际成本 = 0 → 可以"终身免费" ✅
```

> **BYOK 把「持续的算力成本」从 Park 转移给了用户自己。**
> 这不是妥协，这是让 ¥9.9 终身承诺在会计上成立的唯一方式。

## 🏪 1. 商店的三条服务通道

| 通道 | 算力费谁付 | 会员价 | 说明 |
|---|---|---|---|
| **① 下载** | 无人（成本 ≈ 0） | **免费无限** | 会员可下载店内任何公共物品 |
| **② BYOK** | **用户自己** | **免费** | 用户填入自己的 API Key；Park 只提供客户端与协议 |
| **③ 社区 API** | 服务提供方 | **按量计费** | 社区节点提供算力；Park 提供发现、身份、计量、结算 |

**三者关系**：① 是会员权益；② 是"我用自己的电"；③ 是"我买电网的电"。**三者可以混用**——同一个用户可以在下载时用 ①，跑本地模型时用 ②，临时需要大模型时用 ③。

## 🎫 2. 会员凭证：SBT

| 属性 | 值 |
|---|---|
| 价格 | **¥9.9，一次性** |
| 形态 | **SBT（Soulbound Token）**，不可转让 |
| 权益 | ① 无限下载 ② 网络接入 ③ 治理权 ④ BYOK 使用权 |
| 设备席位 | **≤ 4 台硬件**（见 `10_Ticket_Credential_Design.md`） |
| 时效 | **终身** = 代码版本 + 后续升级（不含算力） |

> **技术实现完全复用 `10_Ticket_Credential_Design.md`**：这里的 SBT 就是那份文档中的 **L1 Ticket**，席位、门禁、计量、FROST 门限签名 Issuer 全部沿用。

## 🛡️ 3. 为什么「无限下载」不怕被薅？

**因为下载的东西本来就是开源的。**

这是本产品最重要的一条性质：

| 常见担忧 | 实际情况 |
|---|---|
| 「他 mint 一次然后倒卖下载内容怎么办？」 | 倒卖**已经免费的东西**没有意义 |
| 「有人绕开 SBT 直接拿代码怎么办？」 | ✅ **欢迎**——从 GitHub 直接 clone 即可，这正是 Apache 2.0 的承诺 |
| 「那 SBT 门禁在做什​么？」 | 门禁的不是**内容**，是**会员身份 + 便利性 + 网络接入** |

**SBT 提供的便利性包括：**

- **经过验证的构建产物**（签名、可复现、无后门）
- **一键安装与自动更新通道**
- **精选与策展**（不用自己在 GitHub 上大海捞针）
- **网络接入权**（社区 API、跨节点发现）
- **治理与收益权**

> **结论：这里没有 DRM，也永远不会有。**
> 会员费买的不是"能不能拿到代码"，而是"拿到之后能不能顺畅地用、能不能接入网络、能不能分到钱"。

## 💰 4. 钱怎么分：接 Vault

```
会员支付 ¥9.9
   → 进入 Vault（`05_Mechanism_Design.md` §2 的调节枢纽）
   → 按规则分配给创作者与基础设施
        · Builder Grant   → 公共物品的创作者
        · Infra Mining    → 提供 API/算力的社区节点
```

这与既有机制**完全对齐**：`05` 中 Vault 的 Input 正是 `Ticket Burns`，Output 正是 `Builder Grant / Infra Mining Rewards`。

### ⚠️ 必须解决的分配难题：无限下载会让下载量失真

会员制下"下载"是免费的，会诱发**刷下载量套取分成**。

| 风险 | 缓解方向 |
|---|---|
| 创作者自刷下载量 | **按独立会员去重计数**，同一会员重复下载只算 1 次 |
| 互刷联盟 | 引入**信誉权重**与**随机抽样审计** |
| 下载量与真实价值脱钩 | 加入**实际使用信号**（留存、调用次数）作为辅助权重 |

**这是本产品最需要认真设计的一环**，建议与 `05` 的 Vault 分配算法联合定义，单独立档。

## 🚶 5. 用户旅程

```
1. 访问商店
      → 看到全部公共物品，但下载按钮处于「锁定」状态

2. 点击「¥9.9 铸造会员 SBT」
      → 支付（法币 / 稳定币，走 Paymaster）
      → SBT 铸造到账户

3. 解锁
      → 全部商品可下载，无限次
      → 获得 4 个设备席位（硬件绑定，见 doc 10）
      → 获得网络接入权

4. 使用服务（三选一或混用）
      ├─ 下载到本地，自备算力      → 免费
      ├─ BYOK：填入自己的 API Key  → 免费
      └─ 社区 API：按量付费        → 计量计费

5. 参与治理
      → 持 SBT 即有投票权、仲裁权（Jury）
```

## 🚫 7. 反模式

1. **把下载做成 DRM** —— 内容本来就开源，做锁只会伤害付费用户的体验。
2. **让 Park 承担 API 算力却承诺终身免费** —— 会计上必亏，这正是 BYOK 存在的理由。
3. **把「社区 API」也做成免费** —— 社区节点自付算力，免费等于没人愿意提供。
4. **按原始下载量分配 Vault** —— 必然被刷。必须去重 + 加权 + 审计。
5. **用 Passkey 或机器指纹做席位绑定** —— 见 doc 10，会形同虚设。

## ❓ 8. 待决

1. **Vault 分配算法**：下载量 / 使用量 / 治理投票 的权重如何？（**最关键**）
2. 免费下载是否要限速或限量？（建议：不限量，限并发即可）
3. 社区 API 的定价由谁定：节点自主定价，还是协议统一？ 
4. BYOK 的密钥是否经过 Park 客户端？（建议：**绝不**，仅本地存储，否则失去 BYOK 的意义）
5. 非会员能否下载？（建议：可以，但需自行从源码构建——这是 Apache 2.0 的承诺）
